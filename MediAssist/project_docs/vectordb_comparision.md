MediAssist AI --- Vector Database Comparison and Selection
Document type: Technical decision record
Project: MediAssist AI -- Enterprise Healthcare Agentic AI Copilot
Status: Proposed initial selection
Scope: Vector database selection for fewer than 1 million vectors,
including indexing algorithms and keyword, vector, and hybrid search.
1. Purpose
MediAssist AI uses Retrieval-Augmented Generation (RAG) to retrieve
relevant passages from uploaded healthcare documents. After text
extraction, cleaning, chunking, and embedding generation, the resulting
vectors and their source text and metadata must be stored and searched.

This document compares ChromaDB, Pinecone, Weaviate, and FAISS and
recommends an initial vector store.
2. Project requirements and assumptions
- Expected initial scale: fewer than 1 million vectors.
- Embeddings: generated by ingestion/embeddings.py using
  sentence-transformers/all-MiniLM-L6-v2.
- Embedding dimension: 384 for this model.
- Data: document chunks plus metadata such as source filename, page
  number, and chunk index.
- Search: semantic vector search first; keyword or hybrid search can
  be evaluated later.
- Development: local development on Windows, with deployment options
  to be assessed later.
- Separation of responsibilities: embeddings.py generates vectors;
  vector_store.py handles persistence, indexing, and retrieval.
These are project assumptions, not a measured production capacity
commitment. Performance depends on hardware, metadata, vector
dimensions, concurrency, and document sizes.
3. What is a vector database?
A vector store holds embedding vectors and associates them with records
such as text chunks, IDs, and metadata. At query time, the question is
embedded and compared with stored vectors to find semantically similar
content.

MediAssist pipeline:
1. document_loader.py extracts text.
2. chunker.py cleans and splits text.
3. embeddings.py generates vectors.
4. vector_store.py stores vectors, text, and metadata.
5. retriever.py searches for relevant records.
6. rag_chain.py uses retrieved context to help generate a grounded
   answer.
4. Options compared
4.1 ChromaDB
Type: Open-source vector database with local persistence and
server-backed deployment options.

Indexing: Chroma uses HNSW-based vector indexing in its common
single-node configuration. Deployment modes and details can vary by
version.

Search: Vector similarity, metadata filtering, and current
full-text/keyword and sparse/hybrid capabilities. Verify the exact APIs
for the installed version.

Advantages: - Simple Python integration and low-friction local
development. - Persistent local storage is available through
PersistentClient. - Accepts embeddings generated by our own Sentence
Transformers model. - Offers a path from local development toward
server-backed or managed deployment.

Limitations / considerations: - A local persistent client is
intended for local development and testing; assess server-backed
deployment separately for production. - Monitor memory use as the vector
count grows. - Verify version-specific hybrid-search APIs before relying
on them.

Fit for MediAssist: Strong fit for the first RAG implementation
because it supports local persistence, metadata, and straightforward
Python integration.

Official documentation: - https://docs.trychroma.com/ -
https://docs.trychroma.com/reference/python -
https://docs.trychroma.com/guides/deploy/performance
4.2 Pinecone
Type: Managed cloud vector database.

Indexing: Index implementation is managed by the service. The
application configures vector dimension, similarity metric, and
deployment/capacity options.

Search: Dense vector search, sparse vector support and hybrid
retrieval patterns depending on configuration, plus metadata filtering
and namespaces.

Advantages: - Managed infrastructure reduces database operations
work. - Useful for cloud-hosted applications that need a managed
service. - Supports dense and sparse vector capabilities.

Limitations / considerations: - Requires service credentials and
network access. - Usage and infrastructure can incur costs. - Healthcare
data requires privacy, contractual, residency, and compliance review
before sending it to a hosted service. - Less suitable than a
local-first option for a self-contained prototype.

Fit for MediAssist: Consider for later managed production deployment
if cost and data-governance requirements are acceptable.

Official documentation: - https://docs.pinecone.io/ -
https://docs.pinecone.io/reference/api/2025-10/control-plane/configure_index
4.3 Weaviate
Type: Vector database that can be self-hosted or used as a managed
service.

Indexing: Supports HNSW, flat, dynamic, and HFresh vector index
types. HNSW is commonly recommended for larger collections requiring
fast approximate nearest-neighbor search; flat indexing can suit smaller
collections.

Search: Vector search, BM25 keyword search using an inverted index,
hybrid search combining keyword and vector results, metadata filtering,
and optional reranking integrations.

Advantages: - Integrated vector, keyword, and hybrid retrieval. -
Configurable indexes and metadata filtering. - Suitable when a richer
search platform is required.

Limitations / considerations: - More configuration and operational
concepts than may be needed for the first prototype. - Resource needs
depend on deployment. - Self-hosted and managed modes require separate
cost and operational evaluations.

Fit for MediAssist: Strong alternative if hybrid retrieval becomes
central or a dedicated database service is needed.

Official documentation: -
https://docs.weaviate.io/weaviate/concepts/vector-index -
https://docs.weaviate.io/weaviate/concepts/search/hybrid-search -
https://docs.weaviate.io/weaviate/concepts/indexing
4.4 FAISS
Type: Open-source vector similarity-search library, not a full
database service.

Indexing algorithms: - IndexFlatL2 / IndexFlatIP: exact
brute-force search. - HNSW: approximate nearest-neighbor graph search. -
IVF: partitions vectors into clusters and searches selected
partitions. - Product quantization (PQ) and scalar quantization: reduce
memory usage with accuracy trade-offs.

Search: Vector similarity search. Keyword search is not built in as
a full-text system; hybrid search requires an additional keyword engine
and application-level result fusion.

Advantages: - High-performance similarity search and many index
choices. - Local execution and fine-grained control. - Useful for
research and custom retrieval systems.

Limitations / considerations: - The application must manage document
text, IDs, metadata, persistence, and updates around the index. -
Requires more surrounding application code than a database that stores
documents and metadata directly. - Index types differ in update/delete
support and memory behavior.

Fit for MediAssist: Viable if maximum control over the
similarity-search index is needed, but requires more custom storage and
retrieval code for the initial app.

Official documentation: - https://faiss.ai/ -
https://github.com/facebookresearch/faiss/wiki/Faiss-indexes -
https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index

6. Indexing algorithms in simple terms
Flat / brute-force search
Compares a query vector with every stored vector. It can be exact and
simple, but query work grows linearly with the collection size.
HNSW (Hierarchical Navigable Small World)
Builds a graph connecting nearby vectors. Search navigates the graph to
find approximate nearest neighbors quickly. It trades additional memory
and index-building work for fast search.
IVF (Inverted File Index)
Clusters vectors into groups. At query time, only selected groups are
searched. It can reduce work for larger datasets, but needs
configuration and usually training.
PQ (Product Quantization)
Compresses vectors into compact codes to reduce memory. Compression can
reduce search accuracy, so it should be evaluated against the use case.

For fewer than one million vectors, begin with a standard HNSW-backed
vector database rather than tuning IVF/PQ prematurely. A flat index may
also be sufficient for a small test dataset; measure latency and
retrieval quality before optimizing.
7. Keyword, vector, and hybrid search
Keyword search
Finds records based on literal terms, often using an inverted index and
ranking methods such as BM25.

Useful for: - Patient or document identifiers. - Clinical codes and
abbreviations. - Exact medication names. - Terms that must match
literally.
Vector search
Embeds the question and searches for semantically similar chunks.

Useful for: - Natural-language questions. - Paraphrased questions. -
Conceptually related passages where wording differs.
Hybrid search
Combines keyword and vector results, then fuses or reranks their
rankings.

For healthcare RAG, hybrid search may improve retrieval when a question
combines natural language with exact terms or codes. Implement it after
dense retrieval works, then compare both approaches using a test set.
8. Recommendation for MediAssist AI
Initial selection: ChromaDB with persistent local storage
For the current project stage, choose ChromaDB as the initial vector
store.

Reasons: 1. The application is being developed locally with Python and
Streamlit. 2. embeddings.py generates 384-dimensional vectors using
all-MiniLM-L6-v2. 3. ChromaDB can store supplied embeddings alongside
chunk text and metadata. 4. Persistent local storage is straightforward
for development. 5. It reduces custom index, metadata, and persistence
code compared with building around FAISS. 6. We can implement dense
retrieval first and assess keyword/hybrid options later.
Why not the others first?
- Pinecone: consider it if managed cloud operations become more
  valuable than local-first development, after reviewing costs and
  data governance.
- Weaviate: consider it if integrated BM25/vector hybrid search
  and a dedicated database service become central requirements.
- FAISS: consider it if fine-grained index control is more
  important than built-in document and metadata management.
This is a pragmatic starting decision, not a claim that ChromaDB is
universally best or already proven fastest for MediAssist.

Grounded healthcare response
The vector-store layer should retain, at minimum: - Stable chunk ID. -
Chunk text. - Embedding vector. - Source filename. - Page number where
available. - Chunk index. - Any additional non-sensitive metadata
required for filtering.

Avoid placing patient-identifiable information in metadata unless
required, access-controlled, and approved. A local vector store alone is
not a complete healthcare security solution.
10. Implementation plan
1. Add the ChromaDB dependency to the project.
2. Create or update vector_store.py without changing working
   authentication or dashboard code.
3. Configure a persistent directory under the existing store/ folder.
4. Create a collection whose embedding dimension matches the selected
   model.
5. Add chunk IDs, vectors, text, and metadata in batches.
6. Implement similarity search for a sample question.
7. Verify retrieved chunks and source metadata.
8. Test persistence by restarting the application and querying again.
9. Build a small evaluation set and compare dense retrieval with hybrid
   retrieval.
10. Add deletion/re-indexing behavior so updated or removed documents do
    not leave stale chunks.
11. Acceptance criteria
- [ ] A chunk can be stored with its embedding, ID, text, and
  metadata.
- [ ] Multiple chunks can be inserted in batches.
- [ ] A query embedding retrieves relevant stored chunks.
- [ ] Results include correct source metadata.
- [ ] The index persists across application restarts.
- [ ] Re-indexing does not create unintended duplicate chunks.
- [ ] A document can be deleted or re-indexed without stale records.
- [ ] Search results can be evaluated against expected
  question-to-document matches.
